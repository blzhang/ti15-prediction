# 抄作业页：主赛事对阵表改成可自定义编辑（2026-08-18）

## 背景

抄作业页现在的主赛事那一节（`site/homework.py:bracket_section`）给的是**一份写死的最优填法**：
一张照客户端版式画的 SVG 对阵表 + 14 张逐场卡片，全部由 Python 在构建时渲染。

页面自己承认了这个形态的缺口，就写在图下面那句提示里：

> 注意后面几轮的候选是被前面的选择锁死的：你如果在 A 格改填 Iron Wing，
> E 格的候选也会跟着变，**不能照抄下面这份了**。

也就是说——**只要读者有任何一格想按自己的判断填，整页立刻作废**。而"想赌一把偏离模型"
恰恰是这一页最常见的真实用法（`site/pages.py:368` 那条群介绍里就是这么写的）。

本设计只解决这一件事：**让那张图变成可以自己点的编辑器，你钉住几格，剩下的它替你重算最优。**

## 三个让这件事变简单的事实

**一、`winners[stage][team]` 是边缘概率，与你的填法无关。**
`model/l6_playoffs.py:enumerate_bracket` 产出的 `winners[阶段][队] = P(该队赢下这一阶段那场比赛)`，
其中已经包含了"这支队根本没走到这一场"的情形。所以

    期望答对数 = Σ_场次 P(你填的那支队真的赢下这一场)

是**纯查表**，改变填法不需要重跑任何模拟。这是整个功能能做成纯前端的根本原因。

**二、自洽性是纯结构约束，可以用一个 14 位整数完整表示。**
胜者组 7 场 + 败者组 6 场 + 总决赛 1 场，每场二选一，2^14 = 16384 种自洽填法。
`best_bracket` 现在用 10 层嵌套循环枚举它们；同一件事写成"遍历 0..16383 并按位展开"完全等价，
而且能被 JS 一字不差地照抄。

**三、卡片 PNG 那条渲染路径已经用 `theme` 参数分叉了。**
`site/bracket_svg.py:render(pl, theme)` 的 `"card"` 分支产出长图用的深色 SVG，
加交互只需再加一个默认关闭的 `interactive` 参数，PNG 那份一个像素都不会变。

## 设计决定

### 决定一：把 bit 编码做成 Python 侧的权威实现，JS 照抄

新增 `expand(qf, bits) -> {阶段: 队}`：把 14 位整数展开成一份完整且自洽的填法。
`best_bracket` 改成遍历 `range(16384)` 调它，替换掉现在那 10 层嵌套循环。

**为什么要重构而不是只在 JS 里新写一份**：前端要的正是这个展开函数，
两份独立实现的同一套路径规则（尤其是败者组交叉那两条）迟早会漂移，而漂移的表现是
"页面算出的期望答对数与模型报的对不上"——一个不会崩、只会静静印错数的 bug。
让 Python 侧只有一个权威实现，并用测试把它钉死，JS 照抄它，是唯一不需要跨语言测试就能守住的做法。

位定义（与 `best_bracket` 现有嵌套循环的变量逐一对应，0 表示"上面那个候选"）：

| bit | 场次 | 0 = | 1 = |
|---|---|---|---|
| 0–3 | UBQF1–4 | 对阵里的 a | 对阵里的 b |
| 4 | UBSF1 (E) | QF1 胜者 | QF2 胜者 |
| 5 | UBSF2 (F) | QF3 胜者 | QF4 胜者 |
| 6 | LBR1-1 (败1上) | QF1 败者 | QF2 败者 |
| 7 | LBR1-2 (败1下) | QF3 败者 | QF4 败者 |
| 8 | LBQF-1 (败2上) | 败1上胜者 | **F 的败者** |
| 9 | LBQF-2 (败2下) | 败1下胜者 | **E 的败者** |
| 10 | LBSF (败3) | 败2上胜者 | 败2下胜者 |
| 11 | UBF (G) | E 的胜者 | F 的胜者 |
| 12 | LBF (败决) | 败3胜者 | **G 的败者** |
| 13 | GF | G 的胜者 | 败决胜者 |

加粗的三行是败者组交叉，也是这套规则里唯一容易写错的地方。

### 决定二：钉住的是**队伍**，不是位置；冲突按时间倒序自动松开

用户点某格某一侧 = 钉住"这支队赢下这一格"。重搜时遍历 16384 种，只保留满足全部钉住条件的，取分最高。

**无解时怎么办**：钉住集合带顺序（记录先后）。若当前全部钉住无解，从**最老**的开始逐个丢弃，
直到有解为止。这保证"你最近点的那一下永远生效"，符合直觉，也意味着页面永远不会停在非法状态。

举例（A 格是 Iron Wing vs Team Spirit）：你先在 A 格钉 Team Spirit，
又在 E 格钉 Team Spirit；随后回头把 A 格改钉 Iron Wing。此时 Team Spirit 已被 A 格淘汰，
E 格那个钉无解——按"丢最老的"，先被丢的是 A 格那个钉（它更早）。但丢掉它之后
A 格就回到了自动重搜，你刚点的那一下等于白点了，所以规则要写准：
**丢弃时跳过本次点击的那一格**，从其余钉里按时间从老到新逐个丢。这一例中被丢的是 E 格的钉。

**为什么不钉位置**：位置（"上面那一行"）的含义随前面的选择变化，钉位置会导致
"我明明钉了这一格，怎么队伍自己变了"。钉队伍是用户脑子里实际在做的事。

### 决定三：图由 JS 改节点、卡片由 JS 重建，构建时那份是无 JS 回退

`bracket_svg.render(pl, "page", interactive=True)` 仍然在构建时输出完整的 SVG
（即模型最优那份），并额外给每一行加：

- 覆盖整行的透明热区 `<rect>`，带 `data-stage` / `data-side`
- 会随填法变的元素加 id：`bk-{stage}-{side}-nm`（队名）、`bk-{stage}-{side}-dot`（圆点）、
  `bk-{stage}-p`（百分比）

JS 只改这些节点的属性和文本，不重建整个 SVG——连线、坐标、列头都不会变，重建它们是白费。
JS 未加载或出错时，页面上留下的就是现在这份静态最优填法，功能退化但不残缺。

**渲染始终由 JS 接管，被门控的只有交互**（见决定五）。窄屏下 JS 照样渲染图与卡片，
只是不绑点击、不显示钉住 UI。若改成"窄屏回到 Python 静态渲染"，卡片就要 Python、JS 各留一份，
而那两份迟早会长得不一样——同一个理由已经在决定一里说过一次了。

14 张逐场卡片改由 JS 渲染（容器 `<div id="bkcards">`），内容随填法变：

- 本格两个候选各自赢下这一场的概率，你选中的那个高亮
- 保留一行"这一格所有可能出现的队"（来自 `win_p[stage]` 全表 top4，与填法无关）——
  这是卡片相对于图的增量信息，去掉的话卡片就只是图的重复了

### 决定四：分数条显示"偏离代价"

现在是三个静态数（这份填法期望 / 闭眼乱填 / 理论上界）。改成：

    你这份期望答对 X.XX / 14　｜　模型最优 Y.YY　｜　比乱填多 Z.ZZ

并在偏离时显示 **−0.31 场**：你钉的这几格让期望少了多少。这是自定义编辑真正的信息价值——
不是"随便你填"，而是"随便你填，但我告诉你这一票押下去值多少钱"。

"闭眼乱填"与"理论上界"两个数保持静态（它们是题目的性质，与填法无关），移到说明文字里。

### 决定五：交互只在桌面启用，窄屏是只读的

每行热区在窄屏下约 159×21 CSS px（SVG `min-width: 900px` 横滚，viewBox 1300 → 900px 缩放），
高度只有触摸目标理想值的一半，且要横向滚动才能找到格子——**在手机上这是个会点错的功能，
不是个不好用的功能**。点错还不报错，因为任何一次点击都产生一份合法填法。所以窄屏不启用。

**不改版式来迁就触摸**：版式与客户端逐格对齐是这张图存在的理由（`bracket_svg.py` 模块注释），
为了触摸目标改宽高等于把它放弃掉。

**断点复用 `style.css:387` 已有的 940px**，即 SVG 开始横滚的那条线——交互可用的条件
恰好就是"整张表能一屏放下"。不引入第二个阈值：两个阈值就是两处会各自漂移的常数。

**跟随窗口变化**：用 `matchMedia("(min-width: 940px)")` 的 `change` 事件，
跨过断点时启用/禁用，而不是只在加载时判一次。否则用户把窗口拉宽后会发现还是点不动。

**窄屏必须告诉用户这个功能存在**，否则手机读者永远不知道。图下面那句提示分叉：
宽屏说"直接点图上的队名就能改，剩下的格子会替你重算"，窄屏说"这张表可以自己改——
换电脑打开就能点"。用 CSS 媒体查询切换两段文案，不用 JS，避免无 JS 时两段都显示。

**分享链接在窄屏下仍然可读**：别人在电脑上改好发给你，你在手机上打开要能看到他的填法
（hash 照常解析、照常渲染），只是不能改。这一点不能因为"窄屏禁用交互"就一并砍掉——
读别人的填法本来就是只读操作。

## 改动清单

### `model/l6_playoffs.py`

1. 新增 `expand(qf, bits)`，`best_bracket` 改用它遍历 `range(1 << 14)`，删掉 10 层嵌套循环。
2. `bracket_homework` 新增 `win_p`：`{阶段: {队名: 概率}}`，完整 14×8（用 `win_blend`，
   与现有推荐同口径）。现在只有 `rows[].top` 的前 4 名且 `p > 0.005`，交互时用户可以选到被截掉的那些。
3. `bracket_homework` 新增 `pick_bits`：模型最优那份填法对应的整数，前端的初始状态。

### `site/bracket_svg.py`

`render()` 加 `interactive=False` 参数；`box()` 在开启时加热区 rect 与元素 id。
卡片路径（`theme="card"`）不传该参数。

### `site/homework.py`

`bracket_section()`：卡片三段（`block()` 的三次调用）换成容器 `<div id="bkcards">`，
里面仍填构建时渲染的那份静态卡片当无 JS 回退，JS 加载后覆盖。
分数条换成带 id 的实时版本，图下面那句"不能照抄下面这份了"的提示改写成宽窄屏两段
（`<span class="wide-only">` / `<span class="narrow-only">`）。

### `site/assets_src/bracket.js`（新文件）

`expand(bits)` / `score(picks)` / `bestGiven(pinned)` / 渲染 / hash 编解码 / 事件绑定。
`expand` 与 `model/l6_playoffs.py` 的同名函数逐位对应。

### `site/pages.py`

`homework.html` 的 `extra_js` 在 settled 分支挂上 `bracket.js` 与初始化数据
（现在 settled 分支的 `extra_js` 是空字符串，picker.js 根本没加载）。
资源复制清单 `("style.css", "app.js", "px.js", "picker.js")` 加 `bracket.js`。

### `site/assets_src/style.css`

热区的 hover / 钉住态样式。钉住的格子必须一眼能与"它替我算的"区分开。
窄屏（`max-width: 940px`）下隐藏钉住 UI 与「恢复模型推荐」按钮、热区不加 hover 效果，
并切换那两段提示文案。

## 分享链接

hash 编码 = 14 位选择 + 14 位钉住掩码 → 各 3 个 base36 字符，形如 `#b=1a2b3c`。
无账号、无 cookie、不上传，与 `picker.js` 现有做法一致。
settled 模式下 picker.js 不加载，两套 hash 格式不会打架。

**钉住掩码要一起编码**：只编填法的话，别人打开你的链接看到的是一份"全部由模型算出来的"填法，
分不出哪几格是你自己的判断——而那恰恰是你想分享的东西。

## 测试

新增 `tests/test_bracket_bits.py`：

1. **16384 种 bits 展开后全部自洽**——每格的 pick 必须在该格的两个候选里。
   复用 `test_l6_playoffs.py:test_最优填法本身是自洽的` 的检查逻辑。
2. **重构不改变结果**——`best_bracket` 重构后返回的最优填法、期望答对数与重构前一致。
   旧的嵌套循环实现搬进测试文件当参照实现，两者逐项比对。
3. **`expand` 是双射**——16384 个 bits 产出 16384 份互不相同的填法。
4. **`win_p` 每格概率和为 1**——已有 `test_每场胜者概率之和恒为一` 覆盖了 `winners`，
   这里断言序列化后的 `win_p` 没有在导出环节丢队或丢精度。

5. **JS 的 `expand` 与 Python 的逐位一致**——本机有 node v22，所以这条不靠"照抄"守，
   而是真的跑：pytest 用 `subprocess` 调 node 执行 `bracket.js` 的 `expand`，
   把 16384 种 bits 的展开结果与 Python 的逐项比对。决定一说的"漂移会静静印错数"
   由此变成一条会变红的断言。node 不可用时 `pytest.skip`——它是加固，不是新增的构建依赖。

位定义表（决定一那张）是两边共同的契约，JS 里那段注释必须指回本文档。

## 已知取舍

**卡片的"其它可能"含义变了。** 原来是"这一格 top4 里除推荐外的几支"，
现在是"这一格所有可能出现的队"（与填法无关的全表）。这是更准确的说法——
原来那份也是全表 top4，只是读者会误以为它跟当前填法有关。

**窄屏读者拿不到这个功能。** 决定五的直接代价：手机上这一页仍然只能照抄一份填法。
接受它，因为窄屏下的替代方案（列表式选择器）是另一套渲染路径与另一套版式，
值不值得做要看宽屏版上线后有没有人真的在手机上想改——现在没有依据，不在本设计范围内。

**`greedy_upper`（理论上界）在交互版里的位置下降。** 它解释的是"为什么不能每场都挑赢面大的"，
是题目性质，与你怎么填无关。留在说明文字里，不再占分数条的一格。
