# 选手数据窗口是否该切到当前版本 · 设计文档

日期：2026-08-06 ｜ 状态：已与用户逐节确认

## 1. 背景与目标

有读者提出：**梦幻挑战的选手数据，是不是只考虑 7.41 版本以后的比较靠谱。**

当前选手层三份报告（`model/l4_fantasy_report.py:37`、`model/l4_players_report.py:39`、
`model/l4_extremes_report.py:55`）都硬编码 `since_ts = 1704067200`，即 **2024-01-01 起**，
与游戏版本无关。这个日期当初是"取一个够近又够多"的经验值，从来没有被验证过。

7.41 的发布时间是 **2026-03-24**（OpenDota `constants/patch` 实取），距 TI15 开赛
（2026-08-13）**142 天**。切窗口后的数据量实测：

| 窗口 | 选手-比赛行 | 有数据的选手 | 每人最少 | 中位 |
|---|---|---|---|---|
| 2024-01-01（现行） | 49,762 | 80/80 | 250 | 652 |
| 7.39 起（2025-05-22） | 23,804 | 80/80 | 113 | 309 |
| 7.40 起（2025-12-16） | 12,712 | 80/80 | 43 | 169 |
| **7.41 起（2026-03-24）** | **7,004** | **80/80** | **35** | **94** |

数据只剩 14%，但**没有任何一名选手掉到零**，最少的也有 35 局，高于
`model/l3_player.py:112` 的 `MIN_N_FOR_OWN_GAME_VAR = 20` 门槛。所以这个提议
**技术上可行**，不能用"数据不够"直接否掉，必须拿证据说话。

另一个对该提议有利的事实：**7.41 到 TI15 开赛的 142 天，比近五届任何一届的
"版本年龄"都长**。往年 TI 前一两个月才换版本，"只用当前版本"根本无数据可用；
今年是第一次真的有得选。

| holdout | 开赛 | 当届版本 | 版本年龄 | 上一版本起 | 上版年龄 |
|---|---|---|---|---|---|
| TI2022 | 2022-10-15 | 7.32 | 52d | 2022-02-23 | 233d |
| TI2023 | 2023-10-12 | 7.34 | 65d | 2023-04-21 | 175d |
| TI2024 | 2024-09-04 | 7.37 | 34d | 2024-05-23 | 104d |
| TI2025 | 2025-09-04 | 7.39 | 104d | 2025-02-19 | 197d |
| **TI2026** | **2026-08-13** | **7.41** | **142d** | **2025-12-16** | **240d** |

**目标：用多届 TI 配对回测，判定"切到当届版本起"是否比现行窗口策略更能预测
TI 赛场上的选手数据表现；结论不管好不好看都如实写进报告。本次不改产线。**

### 明确不做（YAGNI）

- 不改任何产线默认 `since_ts`。
- 不动 `model/l3_player.py`（回测复用 `fit_rate_model`，一行不改）。
- 不重跑 `reports/`、不动 `site/`、不重新冻结存证。
- 不做时间衰减加权（见 §7，留作 §3 显示"平滑衰减"时的后续）。
- 不做 blob 三项（smokes / tormentor / courier）——历史届取不到，见 §4。

结论出来之后是否改产线、是否重新冻结，另开一次任务决定。

## 2. 判定规则（预注册）

本节在跑任何回测之前 commit。**跑完再挑对自己有利的指标看，就成了这个项目
自己最反对的事**，所以规则先写死。

**分析单元** = （holdout 届 × 计分项 × 号位）。每个单元内，对该届该号位的选手算

```
spearman( 赛前预测的每局速率, 该届实际的每局均值 )
```

**主判据**：`patch` 臂与 `baseline` 臂在同一单元内的 Spearman 之差。

判定"支持切版本窗口"需要**同时**满足两条：

1. 全部单元的配对符号检验 `p < 0.05` 且中位差 > 0；
2. 四届 holdout 里**至少 3 届**的届内中位差同向为正。

两条都要，是因为单元之间并不独立——同一届里 12 个计分项用的是同一批选手，
符号检验会高估显著性。第 2 条是按届聚类的一致性检查，用来挡住"某一届的
特殊情况撑起了全局显著"。反过来只用第 2 条也不行：四届最多给到 p = 0.0625，
永远够不到 0.05。两条合起来才是这个样本量下能给出的最诚实的判据。

**次要报告项（不参与判定，只作探索）**：按计分项拆开的胜负分布。如果版本效应
集中在绿色池（roshan / tormentor / first_blood 这类跟地图和中立物品改动强相关的项），
而红色池（kills / gpm / creep_score）没有，那是个有价值的观察，但**不能反过来
变成"只对某些项切窗口"的依据**——那是跑完看结果再定规则。

### 为什么主判据是"同号位内排序"

用户确认的判据。梦幻挑战的决策本质是**在同一个槽位里挑人**，绝对数值偏一点
不影响选人；排序错了才影响。绝对误差和区间校准本次不算判据。

## 3. 七个候选臂

全部**相对各届开赛日**定义，因此比较的是"策略"而不是"日期"。所有臂的
`until_ts` 都是该届开赛时间（严格小于）。

| 臂 | since_ts | 含义 |
|---|---|---|
| `all` | 0 | 全部可得历史（数据下限 2020-01） |
| `L955d` | 开赛 − 955 天 | **baseline**：现行产线策略 |
| `L365d` | 开赛 − 365 天 | |
| `L180d` | 开赛 − 180 天 | |
| `L105d` | 开赛 − 105 天 | 与 TI2025 的 `patch` 臂几乎重合，用于暴露"近期性 vs 版本"的混淆 |
| `patch` | 当届版本发布时间 | **treatment** |
| `prev_patch` | 上一版本发布时间 | |

**baseline 为什么是 955 天**：现行产线写的是 `2024-01-01`，那是个日历日期，
不是策略。它对 TI15 的真实含义是"开赛前 955 天"（实测核对：2024-01-01 →
2026-08-13 恰好 955 天）。历史届必须取各自开赛前 955 天，比的才是同一个策略。

**已知弱点**：训练数据下限是 2020-01，而 TI2022 的 `L955d` 起点是 2020-03-04、
TI2023 是 2021-03-01。对 TI2022 而言 `all` 与 `L955d` 几乎重合，这两届对
"all vs L955d"这一组比较基本没有信息量。这不影响本次的主判据
（`patch` vs `L955d`），但报告里必须写明。

### 滑动窗口台阶检验

固定长度 105 天，起点相对开赛日往前滑：`[0,105) / [105,210) / [210,315) / [315,420)` 天。
对每个 holdout 画 Spearman 随距离的曲线，并标注每个窗口跨了几个版本边界。

- 曲线平滑单调下降 → 只是"新数据更好"，跟版本无关，版本边界没有额外信息；
- 边界处出现台阶 → 版本效应真实存在。

**这是整个设计里唯一能把"版本"和"近期"分开的一步**，成本只是同一套代码换
`since / until`。它不参与 §2 的判定，但决定结论怎么解读，也决定 §7 的后续方向。

## 4. 数据与口径

| 项 | 取法 |
|---|---|
| holdout | TI 2022 / 2023 / 2024 / 2025 四届 |
| 排除 TI2021 | 训练侧只有 2020-01 起半年多数据，`all` 与所有短臂差别过小，无对照价值 |
| 训练源 | `data/pro_player_matches_2020_2026.csv` |
| holdout 实际值 | `data/ti_2021_2025_player_matches.csv`，按届按选手取该项每局均值 |
| 计分项 | **12 个 CSV 直取项**：kills / deaths / creep_score / gpm / tower_kills / roshan / teamfight / wards / camps_stacked / runes / first_blood / stuns |
| 排除 blob 三项 | smokes / tormentor / courier 需解 OpenDota JSON blob，`data/pro_blob_stats.csv` 只覆盖 TI15 的 80 名选手、2024-01-01 起，历史届取不到。报告须写明覆盖 12/15 项 |
| 号位 | 队内净资产降序排名的**众数** |
| 号位口径固定性 | 在**全部赛前历史**上算一次，**跨臂固定**——不能每臂各算，否则各臂连分组都不同，就不是配对比较了 |
| 号位稳健口径 | 附带跑一遍 core(1-3) / support(4-5) 两组 |
| 入选门槛 | 该届实际出场 ≥4 局；敏感性另跑 3 和 8 |
| 预测模型 | 直接复用 `model.l3_player.fit_rate_model`，**一行不改**，每个臂只是喂不同的 df 子集 |
| 版本日期表 | 硬编码进 `model/patches.py`，来源 OpenDota `constants/patch`，附取数日期；**跑的时候不打网** |

### 号位推导的验证结果

净资产排名众数已经在 TI15 的 80 名人工策展选手上实测对照过：

- **65/80（81.2%）完全一致**；
- **15 处不一致全部落在 core 内部（1↔2↔3）或 support 内部（4↔5）**，
  没有一处跨越核心/辅助边界。12 处是同队 4↔5 对调。

`ti_2021_2025_player_matches.csv` 自带的 `fantasy_role` 列**不能用**：2240 个 NaN，
且取值出现 0/3/4 等无法解释的值。

回测其实不要求号位标签"正确"，只要求**跨臂一致**——同一套分组同时用于所有臂，
系统性的 4↔5 对调不引入臂间偏差，只降低共同的信噪比。81% 的一致率是加分项，
不是前提。core/support 两组口径作为稳健性检查，因为那个划分与人工策展 100% 吻合。

## 5. 代码结构

新模块 `model/l5_window_backtest.py`，**不修改任何现有模块**：

```
derive_positions(df)                          -> {account_id: 1..5}
window_arms(event_start_ts, patch_ts, prev_patch_ts)
                                              -> {arm: (since_ts, until_ts)}
sliding_arms(event_start_ts, length_days, n_steps)
                                              -> {arm: (since_ts, until_ts)}
holdout_actuals(pm_df, year, item, min_games) -> {account_id: mean}
score_arm(train_df, actual, positions, item)  -> {position: spearman}
paired_sign_test(diffs)                       -> {n_pos, n_neg, median, p}
run_backtest(...)                             -> report dict
```

CLI 产出 `reports/p5_window_backtest.json` + `.md`，`--out` 可覆盖，与既有
`l4_*_report` 的约定一致。

新增 `model/patches.py`：版本名 → 发布时间戳的常量表 + 来源注释。

## 6. 错误处理与"不许悄悄丢数据"

这个项目被读者抓到过数字问题，**静默截断是最容易再被抓的地方**，所以：

- **臂间选手交集**：不同臂下有数据的选手集合不同（短窗口会漏掉赛前歇了几个月
  的人）。配对比较**必须先取所有臂的交集**，否则比的是不同人群。交集前后的
  人数都要进报告。
- **单元跳过**：候选人 < 3 的单元无法算 Spearman，跳过；**跳过数必须出现在报告里**，
  并按（届 × 项 × 号位）列出跳过原因。
- **常数序列**：某单元内预测值或实际值全同 → Spearman 未定义，同样计入跳过，
  不当成 0。
- **NaN**：`teamfight_participation` / `stuns` 在真实数据里有 NaN
  （实测 49762 行里各 54 个），沿用 `fit_rate_model` 已有的 dropna 口径，
  n 按非空计。
- **版本表缺项**：`patches.py` 查不到某版本 → 直接抛错，不静默回退到 `all`。

## 7. 测试计划

`tests/test_l5_window_backtest.py`，TDD，**全部走小 fixture，不读真实 CSV、不打网**
（与本仓既有约定一致）。

| 测什么 | 断言 |
|---|---|
| `window_arms` 边界 | `patch` 臂 since 精确等于该届版本发布时间戳；所有臂 until 等于开赛时间 |
| `L955d` 定义 | TI15 参数下 since 恰好等于 2024-01-01 的时间戳（钉死 baseline 与产线的等价性） |
| 臂间交集 | 构造某臂缺一名选手的 fixture，断言配对集合确实收缩，且报告里记录了收缩人数 |
| 号位推导 | fixture 里把净资产顺序反过来，断言推出的号位跟着反 |
| 号位跨臂固定 | 断言两个不同臂拿到的是同一个 positions 字典对象/取值 |
| 跳过计数 | 构造候选人=2 的单元，断言该单元被跳过且计数出现在报告里 |
| 常数序列 | 构造预测值全同的单元，断言计入跳过而不是记 0 |
| 符号检验 | 已知输入（例如 8 正 2 负）给出已知 p |
| 滑动窗口 | `sliding_arms` 的四段区间首尾相接、不重叠、不漏 |
| 版本表缺项 | 传入未知版本名时抛错，不回退 |

## 8. 预期与失败形态

**一个诚实的预期**：单届单号位的候选人只有 12–18 人，Spearman 的标准误约 0.25。
**很可能四届配对下来根本判不出显著，结论是"没有证据支持切窗口"。**

这不是失败。那也是一个能写进更新日志的答案，而且比拍脑袋换掉 85% 的数据强。
报告必须把"没判出显著"和"证明了两者一样"区分清楚——前者是本次样本量下的
检验力不足，后者本次给不出。

三种可能的结局与对应动作：

| 结局 | 动作 |
|---|---|
| 两条判定都满足 | 另开任务改产线 `since_ts`、重出三份报告、更新日志、重新冻结 |
| 判不出显著 | 产线不动，报告如实记录，README §10 已知限制加一条 |
| 滑动曲线显示平滑衰减、无版本台阶 | 产线不动，把时间衰减加权（半衰期）列为后续候选方案 |
